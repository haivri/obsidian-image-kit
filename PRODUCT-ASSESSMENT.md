# Image Kit and the focus of the image plugins

**Historical assessment.** This document records the initial investigation and first refinement. For the current build and remaining release checks, use README.md, CHANGELOG.md, and bootstrap/README.md. Source and installation statements below refer to that earlier snapshot.

**Update after the UX refinement.** The assessment below records the initial build. The subsequent direction is to continue Image Kit as an image-layout companion. It now adds Edit image to the native action strip, delegates viewing to Fullscreen Image or Obsidian, and uses native resize handles. Reset preserves captions, and the file-deletion action has been replaced with link-only removal. Fullscreen Image now recognizes Image Kit captions. Desktop interaction and a 390-pixel mobile-emulation workflow have been exercised; physical-device validation remains open. The earlier source is preserved in the [pre-change snapshot](/tmp/image-kit-before-native-controls.tar.gz). Other grammar and broader compatibility concerns below remain relevant.


**Recommendation.** Within this image-plugin family, make Simple Gallery the main development investment, maintain Fullscreen Image as a small companion, and continue Image Kit as a focused caption-and-layout trial. The user's daily-use feedback supports continuing this narrow workflow. Image Kit still needs to demonstrate reliability and a substantial workflow advantage before a third public maintenance commitment. Its most promising contribution is a dependable, convenient way to caption and arrange an individual image while keeping its layout in the note.

The decision standard should be the recurring difficulty removed from a real workflow. Feature count, the amount of code already written, and the convenience of having one installation are weaker reasons to support another product. A plugin can be useful without deserving one of a maintainer's two active development slots. Leaving the second slot empty is a valid outcome.

**Evidence and confidence.** This assessment reflects information checked on September 12, 2026. The local source versions are Image Kit 0.1.0, Fullscreen Image 1.4.0, and Simple Gallery 1.8.3. The running primary vault uses Obsidian 1.13.7. Native capabilities and competitor descriptions come from official release notes and project documentation. The quality ranking is an analytical judgment; no comparative usability study or community-demand survey has established a winner.

**The installed build.** Image Kit 0.1.0 is installed in `/Users/robertfleming/vaults/obsidian-vault/.obsidian/plugins/image-kit` and enabled in the running app. Its three runtime artifacts match the production build by SHA-256. All 23 tests pass, the production build succeeds, and lint reports zero errors and zero warnings. Desktop preset, alignment, reset, and viewer-caption interactions were exercised using a temporary test note. Phone emulation at 390 pixels verified touch activation, 44-pixel controls, caption saving, and image visibility after resizing. Physical-device and keyboard behavior still need validation.

The vault-specific settings keep paste/drop interception disabled. Fullscreen Image continues to handle viewing, and Attachment Management retains its existing attachment workflow. Image Kit adds Edit image before the native Edit this block action and preserves native zoom and resize controls. Its explicit fullscreen action delegates to Fullscreen Image or Obsidian. The duplicated viewer and resize handles have been removed from Image Kit. Both installed plugins retain their previous `data.json` files byte for byte.

The Image Kit source repository has no commits. The publisher now supports this state and records an uncommitted development build with artifact hashes and a null source commit. It is not a public release. Fullscreen Image has a small unpublished caption-integration change. Neither repository was pushed. The temporary desktop and mobile test tabs and generated note/image have been removed.

**The native baseline has changed substantially.** Obsidian introduced image dimensions in link syntax in October 2020. The recent change is the interaction around images. The public 1.13 release on July 30, 2026 added the new image experience: fullscreen viewing, movement between a note's embedded images, panning, and easier resizing. Selected images also support keyboard resizing, resetting, and manual size editing. The primary vault already has this release family.[^1][^2]

This changes the business case for a plugin advertised around resizing and zooming. Those are now baseline capabilities. A separate plugin has to demonstrate better interaction in a specific workflow, or provide a useful capability beyond that baseline. The release history also makes continued native improvement plausible, although it does not establish that Obsidian will add captions or image alignment next.

| Job | Current alternatives | Remaining opportunity | Investment decision |
| --- | --- | --- | --- |
| Change an image's displayed width | Native image controls and link dimensions | Convenient named presets applied repeatedly | Small convenience; insufficient by itself |
| Open, zoom, pan, and navigate ordinary note images | Native fullscreen viewer; established viewer plugins | A demonstrably easier interaction sequence | Maintain a focused viewer if the advantage persists |
| Caption and arrange one image | Image Captions; Image Converter; snippets | Reliable visual editing with size, caption, and alignment kept together | Image Kit's best hypothesis; validate first |
| Arrange a sequence of images with explanatory text | Gallery plugins; native Bases for file collections | Authored sequences, sections, captions, and direct editing inside a note | Strongest candidate for Simple Gallery |
| Rename and organize pasted attachments | Existing Attachment Management in the primary vault; other image plugins | Little additional personal benefit established | Leave outside the active Image Kit investment |
| Convert, compress, crop, annotate, or batch-process | Image Converter and dedicated tools | No demonstrated advantage for this project | Decline |

The table combines documented capabilities with recommendations. “Remaining opportunity” describes a hypothesis, not proof that other tools cannot serve it.

**The relevant competition is stronger than the names suggest.** Image Captions already supports caption text in image links, dimensions alongside captions, and alignment. Its current raw README also documents inline Markdown and links in captions, plus external images in Reading view and Live Preview. An older indexed README still describes an external-image limitation; the newer source does not. A new plugin should not be justified using that stale limitation.[^3]

Image Converter already offers visual resizing, alignment and text wrapping, attachment naming, and a broad collection of image-processing actions. Its July 31 release specifically addresses Obsidian 1.13 conflicts, table syntax, and popout-window behavior. That is evidence of both a capable competitor and the continuing compatibility work such a plugin requires.[^4][^5]

There is real historical evidence of integration friction: an Image Converter issue described captions being lost or interfering with resizing and alignment. However, that issue is closed, and newer releases document related improvements. It supports investigating preservation and compatibility; it does not prove that the same failures remain in the current release.[^6]

Image Toolkit is a separate existing project, not this local Image Kit. It already documents fullscreen viewing, toolbar zoom controls, a thumbnail navigation strip, and other viewing operations. Visible zoom buttons therefore provide useful convenience without establishing a unique category. Its original author's maintenance handoff also illustrates why ongoing support capacity matters.[^7]

Obsidian Image Gallery provides folder-driven masonry galleries with its own lightbox. Native Bases cards display files in a gallery-like grid with optional images and configurable fit. These are credible options for browsing a collection. Simple Gallery's stronger prospective position is constructing a particular sequence inside a note, including sections and explanatory captions. That is a narrower claim than being a better gallery for every use.[^8][^9]

**Simple Gallery has the clearest reason for further investment.** Its local implementation supports selected image lists, justified rows, sections, captions, visual reordering, and settings scoped to a gallery or photo. Together, these support a coherent task: assembling a readable visual explanation within a note. A recipe, a project record, or a sequence of observations benefits from the relationship between images and text. The important outcome is how easily someone can create and revise that explanation.[^10]

The recommended promise is: *Arrange a sequence of images and captions directly in your note, with controls that stay out of the finished reading experience.* Prioritize dependable editing, predictable image order, clear caption behavior, and comfortable touch controls. Before adding settings, check whether a user can complete the basic sequence without opening documentation.

This is still a hypothesis about where the strongest contribution lies. Other gallery tools exist, and direct comparisons may show that some needs are already served well. Also, Simple Gallery's custom fenced block is a portability tradeoff: its source remains readable, but another Markdown renderer will ordinarily show a code block rather than a gallery. Protect the ability to recover ordinary image embeds. A narrow “convert back to ordinary embeds” path would be more aligned with trust and longevity than a broad publishing or export system, if such a recovery need appears in practice.

**Fullscreen Image earns maintenance through interaction quality.** The local viewer offers visible zoom controls, bounded panning, a click/tap sequence for returning from zoom and closing, and integration with Simple Gallery captions and navigation. Those are legitimate improvements when they reduce effort during repeated use. They do not have to invent fullscreen viewing to be valuable.[^11]

The distinction between fit and actual size should stay precise. The current viewer resets its scale to a viewport-fitted image. That is “fit to window,” not necessarily a one-image-pixel-to-one-screen-pixel 100% view. For inspecting fine image detail, those are different operations. Clear naming is a small, worthwhile improvement; a larger inspection-tool roadmap needs separate evidence.

Keep this plugin's promise stable. Fix regressions, maintain its gallery connection, and compare its key interactions after relevant native updates. If the built-in viewer eventually satisfies the same needs, retirement with a clear migration explanation would be successful stewardship. It would remove a dependency and return maintenance time. There is no reason to expand the feature list merely to preserve the plugin's independent existence.

**Image Kit's strongest idea is reliable image layout stored with the note.** A canonical link containing caption, alignment, and width has practical advantages: an edit travels with the note, and two appearances of an image can have different layouts. The existing grammar and guarded link-writing code aim to preserve other content and avoid writing over a changed link. That is a sound direction.[^12]

It is also necessary to describe the portability honestly. The image reference and layout text remain in the note when the plugin is removed. Native Obsidian understands the width convention. Image Kit's alignment classes and generated captions still depend on Image Kit or another compatible renderer. Other Markdown applications do not automatically acquire those visual behaviors. The current README's broad statement that everything survives without the plugin needs this distinction.

The product would need to win on the complete interaction: select the appropriate edit control, add a caption, choose placement, resize, continue writing, and later make a change without damaging any of those choices. This is the comparison to run against native controls plus Image Captions. The novelty is not the pipe-separated syntax; a measurable reduction in friction and mistakes could be the contribution.

**Combining the plugins currently increases the maintenance surface.** Image Kit contains about 2,478 lines across its TypeScript source modules, including a 469-line viewer explicitly ported from Fullscreen Image. The standalone viewer is another implementation in its own repository. These counts describe structure, not complexity or quality, but they show that the conglomeration has duplicated an area of responsibility.[^12]

Every additional writer of image links or handler of image gestures must coexist with native controls, editor modes, tables, touch input, themes, and other plugins. Paste/drop additionally interacts with attachment ownership and naming. The primary vault already supplies a concrete example: the most comfortable trial configuration leaves two Image Kit subsystems disabled.

Do not start a shared framework or merge repositories in response. First determine whether Image Kit deserves an ongoing product commitment. If it does, give the viewer one maintained implementation or delegate viewing to the existing companion. Preserve repository boundaries and working versions while that decision remains open.

**The current code is not ready for a public reliability claim.** The following findings come from source inspection and focused reproductions; they are separate from the passing existing test suite.

| Finding | Evidence | Consequence and recommended response |
| --- | --- | --- |
| Reset removes captions | `resetLayout()` turns `![[photo.jpg\|Evidence caption\|center\|400]]` into `![[photo.jpg]]`. The toolbar and commands label this as resetting size and alignment. Reproduced with the actual grammar module. | An action described as a layout reset removes authored text. Preserve captions or explicitly separate destructive clearing. Avoid Reset in the current build. |
| File deletion misses another use in the same note | `otherReferences()` excludes the entire source note. A mock cache containing two references from that note returned an empty list; the deletion path subsequently trashes the file after removing one link. | Another embed can break. Remove file deletion from the narrow product or make reference checks comprehensive and current before deletion. Avoid “Delete image and file” in this build. |
| Some captions do not round-trip | Setting caption `2026` serializes a token that the parser reads as a size, leaving no caption. Alignment keywords can also be interpreted as layout. Numeric case reproduced. | A simple year is a valid caption. Define unambiguous text handling and test the editing round trip. |
| General caption-format compatibility is limited | The sanitizer removes brackets and pipes; captions are rendered as plain text. | Do not imply compatibility with richer captions accepted by other plugins. Preserve pre-existing text or refuse unsupported transformations. |
| External Reading-view decoration appears incomplete | Decoration visits `.image-embed` containers; the code's own DOM description identifies bare `img` elements for remote images in Reading view. | Source-level gap requiring a rendered regression check; do not claim all image forms work everywhere. |
| Caption integration differs between viewers | Standalone Fullscreen Image searches for captions under `figure`; Image Kit creates its caption inside an image-embed container and its own viewer also searches `.ik-embed`. | Automatic viewing in the present coexistence configuration may omit Image Kit captions. Test and define a shared caption contract before advertising seamless integration. |

The first three are focused, reproducible behavior findings. The external-image and caption-integration findings are source-level concerns requiring broader rendered verification. No destructive action was tested on a real vault file. Locations: [grammar](src/grammar.ts), [file actions](src/file-actions.ts), [edit session](src/edit-session.ts), [decoration](src/decorate.ts), [DOM assumptions](src/dom.ts), [original navigation source snapshot](/tmp/image-kit-before-native-controls.tar.gz), and [standalone caption lookup](../fullscreen-image/src/main.ts).

These findings matter strategically because “more reliable integration” is the strongest proposed differentiation. That quality has to be demonstrated before the product can use it as its reason to exist. Passing parser tests and a successful build are useful foundations, but they are not evidence of safe behavior across all the editor interactions.

**A bounded decision process.** Use the installed build to decide whether the narrow idea deserves investment. The following is a proposed evaluation, not an already completed benchmark or a scheduled commitment.

1. Choose a small representative set of ordinary image notes. Compare captioning, alignment, and repeated sizing with the native workflow plus an established caption plugin. Use a scratch vault for changes and fix or exclude the known Reset and deletion issues.
2. Record time, corrective actions, and occasions when source editing is necessary. Include a repeated image, a table image, a long caption, and phone use if that is part of the actual workflow. A smaller feature set that completes the real task reliably can win.
3. Require a clear personal advantage that recurs during normal use. An example decision threshold is roughly halving the effort for a frequent task, or eliminating a repeated frustrating failure. This is a chosen threshold, not a measured claim.
4. Before a public launch, ask a few independent users to perform the same task without coaching. Observe whether they choose the plugin afterward. A small trial reveals interaction problems; it does not measure the entire community's demand.
5. If there is no substantial advantage, keep the experiment private or stop it. If one small improvement to an established plugin would solve the problem, offer that contribution instead of accepting a third release and support obligation.

**The explicit “no” list.** Decline a broad image suite, compression and conversion, annotations, crop/rotate, batch processing, gallery duplication inside Image Kit, attachment-cleanup automation, a new layout cache, and a shared framework built in advance of a proven need. Most are already excluded by Image Kit's repository contract. Also decline small feature requests whose only justification is that they are easy to implement.

For this family, the recommended allocation is one actively improved experience—Simple Gallery—and one intentionally small maintained viewer. Image Kit must earn a place through a better caption/layout workflow. Existing code is useful evidence and reusable work; it is not an obligation to launch another product.
